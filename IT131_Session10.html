Cold open · Shipping & Receiving, Floor 4

Logistics drops off a pallet with three hundred boxes, all addressed to the same building. "Same building," says the Shipping clerk, "but which office?" She checks the labels. Desk 80 is the web team, desk 53 is the directory desk, and desk 49712 is a temp who started this morning. Some boxes are marked signature required, so she numbers them, waits for receipts, and re-sends anything that never got signed for. Others are marked just drop it off. Module 14 · 14.1

What the transport layer does

The network layer gets a packet to the right host. The transport layer gets the data to the right application on that host, and decides how carefully to deliver it.

JobWhat it means
Track individual conversationsA host may have many applications talking at once. Each conversation is tracked separately.
Segment and reassemble dataBig application data is split into pieces small enough to send, then put back together at the other end.
Add header informationPort numbers (and, for TCP, sequence numbers and more) so the receiver knows where each piece belongs.
Identify the applicationThe port number says which application the data is for.
Conversation multiplexingSegments from many conversations are interleaved on the same link, so one big download doesn't block everything else.

The two transport protocols are TCP and UDP. Neither is "better": ITN's phrase is the right protocol for the right application.

Module 14 · 14.2–14.3

TCP vs. UDP

TCP is signature-required delivery: it tracks every byte. UDP is "just drop it off": fast, with almost no overhead.

TCPUDP
ConnectionConnection-oriented: a three-way handshake before any dataConnectionless: no setup
ReliabilityAcknowledgments and retransmissionBest effort: no ACKs, no retransmission
OrderingSame-order delivery, using sequence numbersNo resequencing. Data is reassembled in the order it arrives.
Flow controlYes (window size)No
StateStateful: tracks the sessionStateless
Header20 bytes minimum8 bytes, fixed
PDU nameSegmentDatagram
Typical appsHTTP, HTTPS, FTP, SMTP, POP3, IMAP, SSH, TelnetDHCP, DNS queries, SNMP, TFTP, VoIP, video streaming and conferencing
UDP isn't "broken TCP" A voice call would rather lose a tenth of a second of audio than pause while it waits for a retransmission, because by then the moment has passed. And an application that needs reliability over UDP can build its own. TFTP does exactly that, with simple acknowledgments of its own.

The UDP header (4 fields, 8 bytes)

No sequence numbers, no acknowledgments, no window. That's where the low overhead comes from.

Module 14 · 14.5

Opening and closing a TCP connection

Before TCP sends a single byte of data, the two hosts shake hands. When they're done, each side says goodbye separately.

The six control flags

FlagMeaning
URGThe Urgent field is significant
ACKThe Acknowledgment field is significant. Set on every segment after the first SYN.
PSHPush: hand this data to the application now
RSTReset the connection (error, refused, or timeout)
SYNSynchronize sequence numbers: used to open a connection
FINNo more data from the sender: used to close

Three-way handshake

PC-A (192.168.10.10:49712) connects to SRV1 (192.168.20.100:80). Numbers are relative, as Wireshark shows them: each side's starting number is shown as 0.

#DirectionFlagsSEQACK
1PC-A → SRV1SYN0—
2SRV1 → PC-ASYN, ACK01
3PC-A → SRV1ACK11

ITN gives the handshake three jobs:

  1. 1. It establishes that the destination device is present on the network.
  2. 2. It verifies that the destination has an active service accepting requests on that port.
  3. 3. It tells the destination that the source intends to set up a session on that port.
The three rules that make the numbers work 1. ACK = the next byte expected = received SEQ + data length.
2. SYN and FIN each use up one sequence number, even though they carry no data. That's why the ACK to a SYN is ISN + 1.
3. A pure ACK (no data) does not move the sender's sequence number forward.

Real starting numbers (ISNs) are random 32-bit values like 2,814,005,331. Relative numbering just subtracts them. The pattern is what matters, not the starting value.

Four-step termination

Continuing the same connection after PC-A sent 400 bytes and SRV1 sent 2,920:

#DirectionFlagsSEQACK
1PC-A → SRV1FIN, ACK4012921
2SRV1 → PC-AACK2921402
3SRV1 → PC-AFIN, ACK2921402
4PC-A → SRV1ACK4022922

The client sends FIN, the server ACKs, the server sends its own FIN, and the client ACKs. Each direction closes on its own. Notice the FIN uses up one number: 401 → 402, 2921 → 2922.

Wireshark often shows three, not four If the server has nothing left to send, it combines steps 2 and 3 into a single FIN, ACK. The exam answer is still four steps.

Module 14 · 14.6

Reliability and flow control

Sequence numbers put the data back in order. Acknowledgments say what arrived. The window keeps the sender from flooding the receiver.

Ordered delivery

Segments can take different paths and arrive out of order. The receiver uses sequence numbers to hold early arrivals until the gaps fill, then hands the data to the application in the original order.

Data transfer, byte by byte

DirectionFlagsSEQACKDataWhy
PC-A → SRV1PSH, ACK11400HTTP GET: bytes 1–400
SRV1 → PC-AACK140114601 + 400 = 401: "send byte 401 next"
SRV1 → PC-APSH, ACK146140114601 + 1460 = 1461
PC-A → SRV1ACK40129210One ACK covers both segments. PC-A's SEQ stays 401, because it sent no new data.

Lost data and retransmission

If the sender doesn't get an ACK in time, it re-sends. ACKs are cumulative: an ACK of 1461 means "I have everything before byte 1461". So if the middle segment of three is lost, the receiver can only keep ACKing up to the gap.

  • Without SACK: the sender may re-send everything from the gap onward, including data that already arrived.
  • With SACK (Selective Acknowledgment): if both hosts support it, the receiver also reports the later blocks it did get, so only the missing segment is re-sent.

Window size and MSS

Window sizeMSS (maximum segment size)
What it limitsHow many unacknowledged bytes can be in flightHow much data fits in one segment
Who sets itThe receiver advertises it in every segmentEach host announces its own in the SYN
Typical valueVaries, and changes during the connection1460 bytes = 1500 MTU − 20 IPv4 header − 20 TCP header

Sliding window: the receiver doesn't wait for the whole window before ACKing. It keeps sending ACKs with an updated window size, so the window "slides" forward and the sender rarely has to stop. If the receiver's buffer fills, it advertises a smaller window and the sender slows down. That's flow control.

"Agreed" vs. "announced" ITN's wording suggests the window size is agreed during the handshake. Strictly, each side announces its own window and MSS; nobody negotiates. Either wording gets the same exam answer.

Congestion avoidance

When the network is congested, routers drop packets, and retransmissions make the congestion worse. When TCP detects loss, the source reduces how much unacknowledged data it sends. ITN stresses it's the sender doing this, not the receiver's advertised window. The actual algorithms are beyond this course.

Preview, not on the ITN exam The real mechanisms are slow start, the congestion window (cwnd), and fast retransmit. You'll meet them in later courses.

Module 14 · 14.7

UDP in action

UDP is simple, and that's the point.

  • Low overhead vs. reliability. No handshake, no ACKs, no retransmission. Good for DNS lookups, VoIP, and video.
  • Datagram reassembly. UDP doesn't resequence. Datagrams are reassembled in the order they arrive, and anything lost stays lost.
  • Server processes. A UDP server application listens on a well-known or registered port (DNS on 53).
  • Client processes. The client picks a random dynamic source port and uses it for every datagram in that exchange. The server replies to that port.

Client-server and peer-to-peer

Who asks and who answers?

Client-serverPeer-to-peer (P2P)
RolesA dedicated server answers; clients requestEvery device can be client and server, request by request
ResourcesCentralized on the serverSpread across the peers
ExampleA browser and a web serverTwo PCs sharing a folder or printer, with no server
  • Download = server → client. Upload = client → server.
  • A P2P network has no dedicated server. A P2P application lets a device be client and server in the same conversation.
  • Some P2P apps are hybrid: a central index helps peers find each other, then files move directly peer to peer.
  • Common P2P apps ITN names: BitTorrent, Direct Connect, eDonkey, Freenet. Some are based on Gnutella, where users share whole files. BitTorrent instead grabs pieces from many peers at once.

Web and email protocols

The two protocol families you use most.

The web: HTTP and HTTPS

Module 15 · 15.4

IP addressing services: DNS and DHCP

DNS turns names into addresses. DHCP hands out addresses in the first place.

DNS

  • Hierarchy: root → top-level domains (.com, .org, .net, country codes like .us) → second-level domains, and down. Each server handles its own zone and refers other questions onward.
  • Message format: queries and responses share one format, with Header, Question, Answer, Authority, and Additional sections.
  • Caching: clients and servers remember answers for a while (the record's TTL), so repeat lookups are fast.

DHCPv4

DHCP automatically gives a host its IP address, subnet mask, default gateway, DNS server, and more. The address is leased for a set time. The client must renew before the lease expires, or the address goes back into the pool. DHCP uses UDP 67 (server) and UDP 68 (client).

StepMessageFromDelivery
DDHCPDISCOVERClientBroadcast. The client has no IP address and doesn't know any server. Source 0.0.0.0, destination 255.255.255.255.
ODHCPOFFERServerUnicast to the client's MAC: "here's an address you can have"
RDHCPREQUESTClientBroadcast. Accepts one offer, and tells any other servers their offers were declined.
ADHCPACKServerUnicast: the lease is confirmed and the client can use the address
  • DHCPNAK: the server rejects the request (e.g., the address is no longer valid). The client starts over with DISCOVER.
  • Renewal: the client already has an address and knows the server, so it sends a unicast DHCPREQUEST straight to that server, which answers with DHCPACK.
Footnotes, and a preview In real captures, OFFER and ACK sometimes go to 255.255.255.255, depending on a "broadcast flag" the client sets. The exam answer is Discover and Request broadcast, Offer and Ack unicast. Configuring a DHCP server on a Cisco router, and ipconfig /release / /renew on a client, are CCNA 2 (SRWE) material.

Watch for this

Common Module 14–15 mistakes

These come up every semester.

  • Calling UDP "worse" than TCP. It's a trade-off: speed and low overhead over reliability.
  • Saying ACK = the last byte received. It's the next byte expected.
  • Forgetting that SYN and FIN each use one sequence number, so the ACK is off by one.
  • Moving the SEQ forward after a pure ACK. Only data, SYN, and FIN advance it.
  • Mixing up window size (unacknowledged bytes in flight) and MSS (data in one segment).
  • Saying the receiver's window handles congestion. Congestion avoidance is the sender cutting back.
  • Thinking clients use well-known ports. Clients use a dynamic source port, 49152+.
  • Mixing up a socket (one IP:port) and a socket pair (both ends).
  • Saying DNS is UDP only. ITN says UDP and TCP 53.
  • Saying DHCP uses TCP, or swapping 67 (server) and 68 (client).
  • Swapping FTP's ports: 21 is control, 20 is data.
  • Swapping POP3 and IMAP, or thinking SMTP retrieves mail. It only sends.
  • Reading "Non-authoritative answer" as an error.
  • Expecting LISTENING ports in plain netstat (you need -a), or treating TIME_WAIT as a fault.
  • Thinking the first DHCPREQUEST is unicast. It's broadcast. Only renewals are unicast.

SEQ / ACK

Real-looking numbers

PC-A picks ISN 5000 and SRV1 picks ISN 9000. Fill in the handshake. Then PC-A sends a 1,000-byte request. What acknowledgment number does SRV1 send back?

Show answer

SYN: SEQ 5000. SYN, ACK: SEQ 9000, ACK 5001. ACK: SEQ 5001, ACK 9001. The request also goes out with SEQ 5001, because the third handshake segment carried no data. SRV1 acknowledges with ACK 6001 (5001 + 1000).

MSS & loss

The middle segment goes missing

SRV1 sends a 4,380-byte file. MSS is 1460, and the first data byte is relative 1. How many segments are there, and what are their SEQs? The second segment is lost. What does PC-A ACK, and what does it ACK once the retransmission arrives?

Show answer

4380 ÷ 1460 = exactly 3 segments, with SEQs 1, 1461, 2921. After getting segments 1 and 3, PC-A can only ACK up to the gap: ACK 1461. Without SACK, SRV1 may re-send from 1461 onward. With SACK, PC-A also reports that it holds bytes 2921–4380, so only the missing segment is re-sent. Once it arrives, PC-A sends ACK 4381 (2921 + 1460).

Two tabs and an SSH session

PC-A has two tabs open to http://www.it131.example and an SSH session to R1. Its source ports are 49712, 49713, and 49731. Write the three socket pairs. How does SRV1 tell the two tabs apart?

192.168.10.10:49712 ↔ 192.168.20.100:80

192.168.10.10:49731 ↔ 192.168.10.1:22

TCP or UDP?

Pick the transport

A VoIP call. Downloading a 2 GB ISO over HTTPS. An ordinary DNS lookup. A zone transfer between DNS servers. Copying a config to a TFTP server. Getting an address by DHCP.

Show answer

VoIP: UDP (delay matters more than a lost packet). ISO over HTTPS: TCP 443 (every byte, in order). DNS lookup: UDP 53. Zone transfer: TCP 53. TFTP: UDP 69 (it does its own simple ACKs). DHCP: UDP 67/68.

netstat

"I think I have leftover connections"

A user runs netstat -an and sees:

PC-A
TCP 192.168.10.10:49712 192.168.20.100:443 ESTABLISHED TCP 192.168.10.10:49705 192.168.20.100:443 TIME_WAIT TCP 192.168.10.10:49706 192.168.20.100:443 TIME_WAIT UDP 0.0.0.0:123 *:*

Is anything wrong?

Show answer

Nothing is wrong. There's one live HTTPS session (ESTABLISHED, dynamic source port to well-known 443), and two recently closed sessions in TIME_WAIT that PC-A closed first. Those clear on their own. The UDP row has no state because UDP is connectionless.

DHCP

Name the DORA messages

PC-A boots, and R1 (192.168.10.1) is the DHCP server. Name each message:
1. 0.0.0.0 → 255.255.255.255, UDP 68 → 67
2. 192.168.10.1 → 192.168.10.10, UDP 67 → 68
3. 0.0.0.0 → 255.255.255.255, UDP 68 → 67
4. 192.168.10.1 → 192.168.10.10, UDP 67 → 68
Two days later PC-A renews its lease. What changes?

Show answer

1 DHCPDISCOVER (broadcast), 2 DHCPOFFER, 3 DHCPREQUEST (still broadcast, because the client doesn't have its address yet), 4 DHCPACK. At renewal PC-A already has 192.168.10.10 and knows the server, so its DHCPREQUEST is unicast from 192.168.10.10 to 192.168.10.1, and R1 answers with a DHCPACK.

Email

Phone and laptop

Which protocol carries a message from the sender's client to its mail server? A user reads mail on a phone and a laptop; which retrieval protocol leaves the laptop with the only copy, and which keeps both in sync?

Show answer

Sending: SMTP, TCP 25. Only copy on the laptop: POP3 (TCP 110), which downloads and deletes in ITN's model. In sync: IMAP (TCP 143), which keeps mail on the server.
