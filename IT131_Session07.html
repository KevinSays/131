Module 10

Initial router configuration

Same shape as Session 2's switch walkthrough, same security reasoning — but read the ordering notes below before you run this. Two things must happen before crypto key generate rsa will even work.

Ordering matters 1. hostname and a domain name must both be set before crypto key generate rsa — the key pair is literally named hostname.domain-name, and IOS refuses with "% Please define a domain-name first" if either is missing. 2. username must exist before you rely on login local, or you lock yourself out of the vty lines. 3. ip address and no shutdown are an inseparable pair — more on that below.
Router Initial Configuration (full walkthrough)
! === Step 1: Enter privileged EXEC, then global config === Router> enable Router# configure terminal Router(config)# ! === Step 2: Device name === Router(config)# hostname R1 R1(config)# ! === Step 3: Secure privileged EXEC mode === R1(config)# enable secret Cisco123 ! "enable secret" is hashed. "enable password" is plaintext — never use it. ! === Step 4: Secure the console line === R1(config)# line console 0 R1(config-line)# password ConP@ss R1(config-line)# login R1(config-line)# exec-timeout 5 0 ! auto-logout after 5 min idle — a Module 16 habit, worth planting here R1(config-line)# logging synchronous ! stops console log messages from chopping up the line you're typing R1(config-line)# exit ! === Step 5: Secure remote access with SSH (the complete sequence) === R1(config)# ip domain-name it131.local ! Classic IOS / Packet Tracer: "ip domain-name" (hyphen). ! Current IOS-XE docs spell it "ip domain name" (space) — most images ! still accept the hyphen as a legacy alias. R1(config)# crypto key generate rsa modulus 1024 The name for the keys will be: R1.it131.local % The key modulus size is 1024 bits % Generating 1024 bit RSA keys, keys will be non-exportable... [OK] (elapsed time was 2 seconds) ! Requires the hostname AND domain name set above. 1024 is a lab ! convenience — 2048 is the real-world minimum today. R1(config)# ip ssh version 2 R1(config)# username admin secret Cisco123 ! SSH authenticates a USER, not a line password. This is mandatory. R1(config)# line vty 0 4 R1(config-line)# login local R1(config-line)# transport input ssh R1(config-line)# exec-timeout 5 0 R1(config-line)# exit ! === Step 6: Encrypt the remaining plaintext passwords === R1(config)# service password-encryption ! Type 7 — weakly obscures the LINE passwords only. Contrast with ! "enable secret", which is a real hash. ! === Step 7: Legal banner === R1(config)# banner motd # Enter TEXT message. End with the character '#'. Authorized access only. All activity is monitored.# ! The delimiter (#) must not appear anywhere inside the message text. ! === Step 8: Configure the LAN-facing interface === R1(config)# interface gigabitethernet 0/0/1 R1(config-if)# description LAN-A -- Building 1 users R1(config-if)# ip address 192.168.10.1 255.255.255.0 R1(config-if)# no shutdown %LINK-5-CHANGED: Interface GigabitEthernet0/0/1, changed state to up %LINEPROTO-5-UPDOWN: Line protocol on Interface GigabitEthernet0/0/1, changed state to up R1(config-if)# exit ! === Step 9: SAVE the config === R1(config)# end R1# copy running-config startup-config Destination filename [startup-config]? [Enter] Building configuration... [OK]
Why "no shutdown" is mandatory here — the switch confusion, resolved Every physical interface on a router is administratively down by default — a router out of the box has no active interfaces at all. no shutdown isn't housekeeping, it's the command that turns the port on. A switch access port is the opposite — enabled by default, which is why plugging a cable straight into a factory switch just works. What confuses students is the switch SVI from Session 2 (interface vlan 1), which also needs no shutdown — so the real rule isn't "switches don't need it, routers do." It's: Layer 3 interfaces are shut down by default. Layer 2 switch ports are not. A router's GE port is L3. A switch's SVI is L3. A switch's access port is L2. Watch for the %LINK-5-CHANGED / %LINEPROTO-5-UPDOWN pair — if you don't see both lines, the interface is not up.

Module 10

What genuinely differs from switch configuration

Most of Session 2 carries straight over — enable secret, console/vty security, the whole SSH block, banners, saving. This table is only the parts that don't.

Switch (2960 / C1000)Router (ISR 4321 / 4221)
Physical port, default stateEnabledAdministratively down
IP address lives onOne SVI (interface vlan 1) — a management IP onlyEvery routed interface, one per subnet
switchport commandsYes — mode access, access vlan, etc.Don't exist on a router's GE port
Routing between subnetsOff by default (it's an L2 switch)On by default (ip routing)
Reaching other subnetsip default-gateway — one command, points off-deviceA default route — see the preview below
Number of L3 interfacesTypically one (the SVI)As many as you have ports
The best trap in this session Session 2 taught ip default-gateway on a switch. That command exists on a router too — but Cisco's own documentation says it only functions when ip routing is disabled, and ip routing is on by default on every router. A student who "applies what they learned in Session 2" types ip default-gateway 192.168.1.1 on a router — IOS accepts it without complaint, and it does nothing. No error, no effect. Module 10's own topic title, "Configure the Default Gateway," is actually about configuring hosts and switches to point at the router — the router itself doesn't have a default gateway, it has a default route.
Two more silent-ish failures worth knowing Overlapping subnets on two interfaces: % 192.168.10.0 overlaps with GigabitEthernet0/0/1 — the address is rejected and not applied. Network/broadcast address assigned to an interface (e.g. 192.168.10.0 or .255 with a /24): also rejected, also not applied, with a "bad mask" style error. Both are easy to skip past in a wall of terminal output, and both leave the interface with no IP at all — students then spend twenty minutes debugging a dead interface that was never actually misconfigured, just unconfigured.

So how do two LANs actually talk?

Static routing is CCNA 2 material (Switching, Routing & Wireless Essentials, Module 15), not Module 10. It isn't on the Modules 8–10 checkpoint. It's here because the question is inevitable the moment two routers show up on a diagram, and having the answer beats pretending routing tables are magic for another semester.

Static routes — R1 and R2
! ---------- R1: a specific static route ---------- R1(config)# ip route 192.168.20.0 255.255.255.0 10.0.0.2 ! Syntax: ip route <destination-network> <mask> <next-hop-IP> ! "To reach LAN-B, hand the packet to R2's address on our shared link." ! The next hop is always the NEIGHBOR's address — never our own. ! ---------- R2: a default route ---------- R2(config)# ip route 0.0.0.0 0.0.0.0 10.0.0.1 ! R2 is a stub — one way out of its own networks, so a default route ! is the right tool. 0.0.0.0 0.0.0.0 matches EVERY destination, which ! makes it the last resort: the router always prefers the longest ! (most specific) prefix match it has.
The whole lesson, in one sentence A static route is one-directional. Configure R1 and forget R2, and a ping from LAN-A arrives at LAN-B and dies there — it's the reply that has nowhere to go. Students read that as "ping failed" and go straight back to staring at R1. Routes must exist in both directions, on both routers.

The highest-yield fact in this section One ip address plus one no shutdown produces exactly two routing-table lines — a C and an L. If a student sees only one, or neither, the interface isn't up. [1/0] is [administrative distance / metric] — AD 1 is the default for a static route, and a connected route's AD 0 is why it always wins over a static route to the same network.

Module 10

Verification commands

What each one is actually for, not just what it prints.

CommandAnswers
show ip interface brief"Are my interfaces on and addressed?" Fastest sanity check on a router. Status = Layer 1 (carrier present?), Protocol = Layer 2 (line protocol up?). Only up/up is good.
show ip route"Does this router know how to reach that network?" No matching entry (and no default route) means the packet gets dropped, with an ICMP Destination Unreachable sent back.
show running-config"What is configured right now?" — RAM, not what boots next time.
show startup-config"What will it look like after a reboot?" If it differs from running-config, you haven't saved.
show cdp neighbors"Is there a Cisco device on the other end of this cable, and which port?" Layer 2 — works even when IP addressing is completely broken. (Module 17 material — preview.)

Try it — the host side still applies Session 2's ping ladder carries over unchanged, with one addition: if ping <default gateway> works but ping <remote LAN host> fails, run tracert from the PC. The hop where it stops is exactly which router is missing a route — the fastest diagnostic there is for "static route configured on only one side."

Watch for this

The most common Module 10 mistakes

In roughly the order you're likely to hit them.

  • Forgetting no shutdown — interface stays administratively down, no C/L route appears at all.
  • Configuring the IP on the wrong interface — easy when a diagram's port order doesn't match the CLI's.
  • PC's default gateway is wrong or unset — same-LAN pings work, everything off-subnet fails, and the router gets blamed.
  • Assigning a network or broadcast address to an interface — rejected, and the interface is left with no IP.
  • Overlapping subnets on two interfaces — rejected with "overlaps with," address not applied.
  • Using ip default-gateway on a router — accepted, does nothing, no error (see the trap above).
  • Static route configured on only one router — the request arrives, the reply has nowhere to go.
  • Putting the local network in an ip route statement instead of the remote one.
  • Using the router's own interface address as the next hop instead of the neighbor's.
  • Forgetting copy running-config startup-config — same lesson as Session 2, more painful on a longer config.

Midterm

Cross-module review

If you can answer these three cold, Modules 1–10 have landed. All three come straight out of material already covered — this is recall, not new content.

  • C vs. L in a routing table. C is the network the interface sits in; L is the interface's own /32 address. Both appear together, or neither does.
  • When does a host ARP for the destination vs. the gateway? Same subnet → ARP for the destination directly. Off-subnet → ARP for the default gateway, never the far-off target (Session 6).
  • What changes at each router, what doesn't. The frame is discarded and rebuilt at every router hop (new MAC addressing); the packet's IP addresses ride end-to-end, untouched (Sessions 4 & 6).

Worked examples

Think it through before you expand the answer.

Router boot

Why won't it ping?

A fresh router has ip address 192.168.1.1 255.255.255.0 configured on G0/0/1. A PC plugged into that LAN can't ping the router at all. show ip interface brief shows the interface as administratively down / down. What's the single missing command?

Show answer

Answer: no shutdown. Unlike a switch port, a router's physical interface starts administratively down and stays that way until explicitly enabled — configuring an IP address alone doesn't turn the port on.

The gateway trap

Accepted, but does nothing

A student, fresh off Session 2, types ip default-gateway 192.168.1.1 in global config on a router. IOS accepts it with no error. Two weeks later, off-subnet traffic still isn't reaching anywhere. Why did the command not help?

Show answer

Answer: ip default-gateway only takes effect when ip routing is disabled — and ip routing is on by default on every router. The command is legal syntax, gets accepted, and simply does nothing. A router needs a default route (ip route 0.0.0.0 0.0.0.0 <next-hop>) to send unmatched traffic somewhere, not a default gateway.

Static routing

Half the route

R1 has ip route 192.168.20.0 255.255.255.0 10.0.0.2 configured. R2 has no static routes at all. A PC on LAN-A pings a PC on LAN-B. What happens?

Show answer

Answer: The ping request arrives fine — R1 knows how to reach 192.168.20.0/24 and forwards it, and R2 is directly connected to that LAN so it delivers the packet. But the reply, generated by the LAN-B host and destined for 192.168.10.0/24, has no route on R2 and gets dropped there. The ping times out, and the failure looks like it's on R1's end even though R1's configuration was correct — a static route only tells its own router how to send, never how to receive a reply.

Reading the table

C, L, or S?

show ip route on a router shows: C 10.0.0.0/30 is directly connected, GigabitEthernet0/0/0, L 10.0.0.1/32 is directly connected, GigabitEthernet0/0/0, and S 192.168.20.0/24 [1/0] via 10.0.0.2. In one sentence each, what produced every line?

Show answer

C: automatic, the moment the interface has an IP address and is up/up — this router has a presence in 10.0.0.0/30. L: automatic alongside every C route — this router's own address, a /32 host route. S: someone typed ip route 192.168.20.0 255.255.255.0 10.0.0.2 by hand.
