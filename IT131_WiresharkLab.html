What is it

Pcap: packet capture, exactly as it crossed the wire

Wireshark doesn't create traffic — it decodes frames a NIC already handles every second. A pcap file just records them, unsummarized, in order.

Note

The capture used throughout this page was taken with dumpcap on a laptop's wlan0 interface doing normal things — a Teams call, some browsing, Steam running in the background. Not a special "hacking" artifact. A recording of whatever a NIC already handles every second.

  • .pcap — the original format: one global header, then a flat list of packet records.
  • .pcapng — "next generation," what Wireshark writes by default now. Same idea, but each packet can carry its own metadata block.
  • Nothing pre-decoded. Wireshark parses headers live, every time the file is opened.
  • Ground truth. Configs and logs say what a device was supposed to send; a capture says what it actually put on the wire.

The interface

Wireshark's three panes

Every capture window is the same three panes, top to bottom. Learn the order and you can read any pcap.

PaneWhat it showsHow to use it
Packet ListOne row per frame, in capture order, with Wireshark's auto-summary in the Info column.Scan here first — color rules (below) flag protocol families before you read a single field.
Packet DetailThe selected frame, decoded and nested exactly like the protocol hierarchy above — Ethernet → IP → TCP → TLS.Expand one layer at a time. Each layer is that protocol's header fields, human-labeled.
BytesThe raw hex/ASCII of the frame.Click any field in Packet Detail — the exact bytes behind it highlight here. Nothing is hidden.

Default color rules

ColorMeans
Light greenHTTP traffic
Light blueTCP, no errors
Light yellowUDP
LavenderTCP SYN/FIN — connection setup/teardown
Dark red / pinkTCP errors — retransmits, resets, out-of-order
Watch for dark-red rows In a healthy capture they're rare. A pcap that's mostly dark red is your first clue something's wrong on the wire — packet loss, a flapping link, congestion.

Case walkthrough

Four real exchanges, frame by frame

Frame numbers below match 131_wireshark_lab.pcapng — a 143-packet teaching slice cut from the full capture with dhcp || arp || http || tcp.stream eq 3 || dns.qry.name=="teams.cloud.microsoft" || dns.qry.name=="s-0005.dual-s-msedge.net". Open it and follow along.

1 · ARP — "who has this IP?"

Before any IP packet can leave the laptop for its default gateway, the OS needs the gateway's MAC address. ARP asks on the local segment — a Layer 2 broadcast, no IP header required.

FrameSrc MACQuestion / Answer
36e4:55:a8:1c:58:8cwho-has 10.209.108.92? Tell 10.128.128.128
3700:72:ee:af:39:f3is-at 00:72:ee:af:39:f3 — reply

2 · DHCP — lease renewal, not a fresh lease

Textbook DHCP is four steps — Discover, Offer, Request, Ack (DORA). This capture only shows two, because the laptop already had a lease when capture started; this is a renewal, not a new lease.

FrameMessageWhat's happening
61DHCP RequestClient asks the server to extend its current lease — no Discover/Offer needed, it already knows the server.
62DHCP ACKServer confirms — same IP, fresh lease timer.
Worth knowing DORA only happens once per lease lifetime. Most DHCP traffic you'll ever capture on a running network is this two-step renewal.

4 · TCP handshake → TLS 1.3 — one stream, start to finish

tcp.stream eq 0 in the lab file:

Framet (s)DirectionFlags / Info
30.000Client → Server[SYN] Seq=0
70.034Server → Client[SYN, ACK] Seq=0 Ack=1
80.034Client → Server[ACK] Seq=1 Ack=1
90.035Client → ServerTLS Client Hello — SNI = teams.cloud.microsoft (plaintext, readable)
120.060Server → ClientTLS Server Hello, Change Cipher Spec, Application Data
14–170.061Client → ServerChange Cipher Spec, then Application Data — everything from here is encrypted
The one plaintext field that matters most Server Name Indication (SNI) in the Client Hello. Even though the rest of the session is encrypted, SNI names the hostname you connected to — exactly how this capture's DNS-name list was reconstructed without decrypting anything.
Sidebar — where did HTTP/3 go? 4,466 frames here are QUIC — HTTP/3 running directly over UDP/443, not TCP. Filter tcp.port==443 expecting "all the HTTPS" and you'll miss most of it. Try quic and compare frame counts.

HTTP

Read the plaintext request

Apply http.request. Find the request to ping.archlinux.org, expand the Detail pane, and read the full plaintext request. Then find its response and note the Content-Type.

Show answer

Frame 34 is GET /nm-check.txt HTTP/1.1 to ping.archlinux.org. Frame 35 is the response — HTTP/1.1 200 OK, text/plain. This pair is exactly what SSH/TLS exist to prevent from being readable — here it's fully visible because HTTP carries no encryption at all.

TLS

Find another SNI

Apply tls.handshake.extensions_server_name. Pick a Client Hello that isn't the Teams example from the walkthrough above. What hostname does it reveal?

Show answer

Answers vary by which frame is picked — the lab file also contains Client Hellos naming other Microsoft/Teams-related hosts. The point of the exercise: SNI makes every HTTPS destination visible without decrypting a single byte of the session that follows.

TCP streams

Confirm the stream index

Right-click any TCP packet → Follow → TCP Stream. Confirm the stream number matches what the Detail pane's TCP layer reports under [Stream index].

Show answer

They always match — "Follow TCP Stream" is just a filtered view (tcp.stream eq N) built from that same field. It's the fastest way to isolate one conversation out of thousands of packets without typing the filter by hand.

QUIC vs. TLS

Which protocol actually carried more?

Apply quic, note the frame count. Apply tls, note that count. Which protocol carried more of this capture's encrypted traffic?

Show answer

Neither is a fair comparison of "HTTPS traffic" on its own — QUIC (4,466 frames) is HTTP/3-over-UDP, and TLS (5,744 frames) here is mostly TLS-over-TCP for older/non-QUIC connections. Together they show that a modern capture's "encrypted web traffic" splits across two different transport protocols, not just TCP/443.
