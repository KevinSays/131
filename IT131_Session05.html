Overview

What Session 5 covers

Module 6 gave you the generic shape of a Layer 2 frame and introduced the MAC address. Module 7 is what a switch actually does with both — how it reads the Ethernet II frame fields, how it builds its own address book instead of being handed one, and the two competing philosophies for how fast to forward a frame once it knows where that frame is going.

  • Identify the fields of an Ethernet II frame
  • Describe the structure of a MAC address and how the OUI identifies the vendor
  • Explain how a switch dynamically builds and ages out its MAC address table
  • Compare store-and-forward and cut-through switching, and their trade-offs
  • Explain duplex and speed mismatches, and what auto-MDIX solves
Where this goes next The MAC address table you learn to read here is the same structure the ARP incident file (Module 9, "The Impersonator") ultimately corrupts — a switch that's been fed a spoofed entry starts sending traffic to the wrong desk without ever knowing it made a mistake.

Module 7

The Ethernet II frame, field by field

Module 6 covered the generic Layer 2 frame — start/stop, addressing, type, data, FCS. Ethernet II is the specific implementation almost every wired network actually runs. Same job, concrete field sizes.

FieldSizePurpose
Preamble & SFD8 bytesAlternating 1s and 0s that let the receiving NIC's clock sync up, ending in a Start Frame Delimiter that marks "the real frame starts now."
Destination MAC6 bytesAddress of the next desk over — not necessarily the final destination, just the next hop.
Source MAC6 bytesAddress of the device that put this frame on the wire.
Type2 bytesIdentifies the Layer 3 protocol riding inside — 0x0800 for IPv4, 0x86DD for IPv6.
Data46–1500 bytesThe packet handed down from Logistics. Padded up to the 46-byte minimum if the packet is smaller.
FCS4 bytesTrailer — lets the receiver verify the frame arrived intact. A failed check means the frame is silently dropped.
The size limits matter Minimum frame size is 64 bytes, maximum is 1518 bytes (Preamble/SFD isn't counted in either). Anything shorter than 64 bytes is a "runt" — almost always evidence of a collision. Anything longer than 1518 without being explicitly configured as a jumbo frame is a "giant." Both are discarded.

Module 7

MAC address structure

A MAC address is 48 bits, written as 12 hex digits — and it isn't random. It splits cleanly into two halves, and the first half tells you who manufactured the card.

Bits 1–24Bits 25–48
OUI (Organizationally Unique Identifier) — assigned to the manufacturer by the IEEE. Every NIC that vendor builds starts with this prefix.Vendor-assigned — a unique value the manufacturer stamps on each individual NIC. Never reused within that OUI.
MAC typeWho receives it
UnicastOne specific NIC — the normal case, one sender to one receiver.
BroadcastFF:FF:FF:FF:FF:FF — every device on the local segment. ARP requests use this.
MulticastA defined group of interested devices, not everyone — used by protocols like OSPF that only need a subset of neighbors to listen.
Carried over from Module 6 Still hop-to-hop, not end-to-end — a switch never rewrites the MAC addressing on a frame it forwards, it only reads it to decide which port to send the frame out.

Module 7

How the address book gets built

Nobody hands Local Dispatch its address book. It builds one itself, one incoming frame at a time — and it only ever learns source addresses, never destinations.

Cold open

A frame lands on Port 3 with a source address Local Dispatch has never seen. It doesn't ask who that is — it just writes it down: "whoever this address belongs to sits behind Port 3." That's the entire learning process, repeated on every single frame.

StepWhat happens
1. ExamineA frame arrives on a port. The switch reads its source MAC address.
2. LearnIf that source address isn't already in the table, add it: source MAC → the port it just arrived on.
3. Look up destinationThe switch checks the table for the frame's destination MAC address.
4. Forward, filter, or floodKnown and on a different port → send out only that port (forward). Known and on the same port it arrived on → drop it, the destination already heard it (filter). Unknown, or broadcast/multicast → send out every port except the one it arrived on (flood).

Entries don't live forever Each entry carries an aging timer (default 300 seconds on most Cisco switches). No traffic from that address before the timer expires, and the entry is dropped — the next frame to that destination gets flooded again until the switch relearns where it lives.

Module 7

Switching forwarding methods

Once the switch knows which port to use, it still has to decide when to start sending — wait for the whole frame to arrive first, or start relaying it out the destination port before it's even finished coming in.

MethodHow it worksTrade-off
Store-and-forwardReceives the entire frame, checks the FCS, and only forwards it if the check passes.Slower (adds latency) but never forwards a corrupted frame. Default and most common on modern switches.
Cut-throughReads only the destination MAC address, then starts forwarding immediately — before the rest of the frame has even arrived.Lower latency, but can forward a frame that turns out to be corrupted, since the FCS isn't checked first.
Fragment-free (variant)A middle ground: waits for the first 64 bytes before forwarding — enough to catch most collision fragments — then forwards without waiting for the full frame.Faster than store-and-forward, catches more errors than plain cut-through.
Exam framing If a question says "checks for errors before forwarding," that's store-and-forward. If it says "starts forwarding as soon as it reads the destination address," that's cut-through. Fragment-free only comes up if the question specifically calls out the 64-byte checkpoint.

Module 7

Switch port settings

Two devices on the same link have to agree on how to use it. When they don't, the link usually still comes up — it just performs badly, which makes this a classic troubleshooting trap.

SettingOptionsNotes
DuplexHalf vs. fullHalf-duplex: send or receive, never both at once — the old shared-medium model, needs CSMA/CD. Full-duplex: send and receive simultaneously — the norm on switched links, no collisions possible at all.
Speed10/100/1000 Mbps, etc.Both ends of a link should run the same speed. Auto-negotiation usually handles this without intervention.
Auto-MDIXEnabled/disabledAutomatically detects whether a straight-through or crossover cable was plugged in and adjusts the port internally — the reason you rarely need to care which cable type you grab anymore.
The trap A duplex mismatch (one side full, one side half) doesn't take the link down — it degrades it. The full-duplex side transmits whenever it wants; the half-duplex side, still playing by collision rules, treats that as a collision and starts dropping/retransmitting frames. Symptom: a link that's "up" but slow and full of late collisions — not a link that's obviously broken.

MAC address table

Learn, then decide

A switch's MAC address table is empty. A frame arrives on Port 1 from AA:AA:AA:AA:AA:AA, destined for BB:BB:BB:BB:BB:BB. What does the switch do with this frame, and what does its table look like afterward?

Show answer

Answer: The switch first learns the source: AA:AA:AA:AA:AA:AA → Port 1 is added to the table. It then looks up the destination, BB:BB:BB:BB:BB:BB — not found, since the table only had one entry and it isn't this one. With no match, the switch floods the frame out every port except Port 1. The table now has exactly one entry: AA:AA:AA:AA:AA:AA → Port 1.

Forward, filter, or flood

Same port, different frame

The table already has AA:AA:AA:AA:AA:AA → Port 1 and BB:BB:BB:BB:BB:BB → Port 1 — both devices sit behind the same downstream hub on Port 1. A frame arrives on Port 1 from AA to BB. What does the switch do?

Show answer

Answer: It filters the frame — drops it entirely. The destination (BB) is known to live on the exact same port the frame arrived on, meaning BB already received the frame directly over the shared segment. Forwarding it back out Port 1 would just be noise.

Store-and-forward vs. cut-through

Pick the method

A switch is dropping a noticeable number of frames that turn out to be corrupted on arrival, but network engineers want the lowest possible latency for a latency-sensitive application. Which forwarding method fits, and what's the trade-off?

Show answer

Answer: This is a genuine trade-off, not a trick — cut-through gives the lowest latency, since it starts forwarding right after reading the destination MAC, but it will forward those corrupted frames rather than dropping them (the FCS never gets checked before forwarding). Store-and-forward catches every corrupted frame via the FCS check, at the cost of added latency from buffering the whole frame first. Fragment-free is the compromise: waits for the first 64 bytes, catching most collision-related corruption, without waiting for the full frame.

Duplex mismatch

Diagnose the symptom

A link light is green and the interface shows "up," but a user reports the connection is slow and a show command on the switch reveals a climbing count of late collisions on that port. What's the likely cause?

Show answer

Answer: A duplex mismatch. One side of the link is running full-duplex and transmitting whenever it has data, while the other side is still running half-duplex and interprets that overlapping traffic as a collision. The link never goes down — it just performs badly, which is exactly why duplex mismatches are a classic "it's up but it's slow" troubleshooting case rather than an obvious outage.
